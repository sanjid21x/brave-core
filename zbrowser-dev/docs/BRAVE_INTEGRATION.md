# Production integration plan

## 1 — Baseline and identity
Build upstream unchanged from a pinned stable Brave Core revision. Record SHA, Chromium revision, GN args, SDK and NDK versions. Make one branch for Z branding and a second for torrent integration. Set the actual Android application ID to `com.sanjid.browser` through the checkout's manifest/GN branding settings, not a global replacement of Java package names. Add original vector Z adaptive/monochrome icons, Android splash theme, app labels; audit OAuth, update URLs, default-browser registration, FileProvider authorities and signing. Smoke-test normal tabs, private tabs, Shields, bookmarks, downloads and startup before integrating.

## 2 — Engine selection and packaging
Preferred: FrostWire jlibtorrent + libtorrent C++ over JNI, with a published AAR for the lab. It avoids implementing BitTorrent yourself; keep native engine version up to date and review upstream license notices. Alternative: directly build libtorrent C++ with the matching Chromium Android NDK, custom JNI and GN; more flexible, more work. WebTorrent is not the initial choice because browser/WebRTC peers differ from standard BitTorrent peers and background Android integration is harder.

For Brave, inspect actual GN AAR import examples (`android_aar_prebuilt`) and target dependency graph; declare the pinned AAR and each required native dependency, Java sources and resources in the correct GN targets, not a standalone Gradle dependency in the browser. Verify native libraries in actual APK modules per ABI, library load order, native symbol isolation, libc++ compatibility (do not overwrite Chromium's runtime), 16KB ELF and ZIP alignment, manifest merges, shrinker/JNI keep rules, transitive dependencies, licensing and security updates. A conflict requires rebuilding the engine against the same toolchain or isolating its process. No placeholder GN files are generated in this kit.

## 3 — Service / durable lifecycle
Use a single engine session for the normal browser profile, worker thread for native calls, and an event-driven repository (coalesce state updates about once a second). Production engine should be in a dedicated app-owned service/process with a typed binder or callback boundary; test process death. Adopt user-initiated data transfer jobs on supported Android versions if suitable, otherwise legal foreground dataSync service with user-visible notification and Android 15 timeout handling. Save fast-resume data and stop promptly on timeout. Never start torrent automatically on boot or in private mode. Private mode must not import or log torrent metadata without explicit warning and consent; simplest first version disables it. Engine does not route through Brave Shields or make users anonymous. Peer IP exposure and upload warning before starting.

## 4 — Intake and metadata
Hook user-initiated external `magnet:` navigation at the browser's verified external-protocol handler; pass to internal confirmation instead of silently downloading. Do not intercept unrelated schemes or auto-start from a redirect. For .torrent, keep Brave's file download and offer `Open in Z Torrent` upon completion; read its content URI with bounded stream. Add document picker import and paste link from Downloads. Parse/validate source, canonicalize v1/v2 infohash, deduplicate, cap metadata size and file count, reject unsafe paths/symlinks, malformed metadata, unsupported formats, and warn before huge allocations. Use metadata-only transfer for magnets in production, allow file selection before payload, then apply priorities through engine and start on confirm. The lab downloads directly after confirmation (not metadata-only).

## 5 — Persistence and storage
Use Room or existing Chromium-backed app store for torrent records (stable hash, display title, job ID, profile, state, selected file IDs, storage URI, timestamps, upload policy, source handle). Store sensitive magnet/tracker parameters privately; never export tokens. Save engine fast-resume state via async resume alerts to temp files and atomic rename; on restart restore explicitly, honor paused state, verify pieces as needed. Engine needs random access to real paths: stage in app-specific storage or native FD-backed storage integration. After engine validates completion, copy selected files into MediaStore.Downloads or SAF folder, finalize pending rows, keep staging for opted-in seeding. Verify size/hash, reserve extra copy space, handle collision, cancellation, partial destination cleanup, low storage, permissions. Never convert a SAF URI into a guessed path. Separate Remove record, Remove torrent + private data, Delete exported files.

## 6 — Unified Z Downloads
Chromium's download provider and coordinator are the source of truth for HTTP/HTTPS. Inspect `chrome/browser/download/internal/android/.../download/home` and `OfflineContentProvider` in pinned checkout (paths vary). Add a `TorrentTransferProvider` adapter in the actual host target: snapshot/event stream, pause/resume/remove by typed ID, completed file URI, diagnostics. Use the included `Transfer` and `TransferIndex` as a neutral example; expand for full durable records and callbacks. Combine existing HTTP, media, torrent and conversion providers in a single Downloads ViewModel/coordinator, never insert P2P entries into Chromium's HTTP download DB or use Android DownloadManager for peer traffic. Prefix IDs by engine to prevent collisions. Preserve normal Brave downloads and progress notifications. One scheduler allocates budgets across HTTP connections and P2P peers, prioritizing foreground browsing and user rules. Separate HTTP parallel Range settings from torrent peer/slot limits.

## 7 — UI / settings
Build Z liquid-glass styled downloads screen using existing native UI infrastructure. Horizontal tabs All / Active / Paused / Completed / Failed / Torrents. Compact rows: title, size, progress, DL and UL speeds, ETA, connected peers/seeds, status; details: files, priority, tracker status (redacted), share ratio, piece integrity and storage. Include explicit add magnet/import buttons, folder picker, queue priority, pause/resume/retry/remove, bulk actions, seeding toggle, ratio/time stop, Wi-Fi-only, metered warning, global/per-job upload/download cap, peer connection limits, notification controls and export/open. Default pause seeding when completed unless opted in; data can upload during acquisition. No fake values. Unknown totals/ETA show dash. Do not display torrent links in automatic playback-only media detector. Route completed supported media into Z converter using content URIs, never mutate seeding files. Dashboard counts verified bytes, completed downloads and active P2P jobs, excluding private data. Respect reduced motion and use translucent fallback rather than expensive blur on unsupported devices.

## 8 — Diagnostics / testing
Log event categories engine lifecycle, state transition, disk error, tracker failure type (not address), native ABI, resume save/restore, foreground timeout, export failure. Bounded log ring buffer opt-in; redacted local export; exclude IPs, tracker tokens, infohash/magnet, full URLs, titles and paths. Unit test contract, input parser, dedup, state machine, settings, queue, URI storage. Device integration test small authorized locally seeded torrent and official Linux ISO, v1/v2 magnets, dead swarm, duplicate, file selection, pause/resume, app kill, network changes, low storage, cancellation, 16KB pages, process isolation, foreground timeout, simultaneous HTTP and torrent, private mode, file opening. Verify piece hashes and resulting files; no mock success. Only mark release when build and tests pass.

## Suggested release milestones
0.1.0: independent engine lab and neutral contract (included). 0.2.0: actual upstream fork, rebranding and GN integration with internal torrent screen. 0.3.0: persistent queue, metadata-only confirmation, unified Downloads provider, user settings. 0.4.0: playback-only media detection, HTTP Range acceleration, HLS/DASH where authorized, converter. 0.5.0: full Liquid Glass UI, horizontal browser tabs, Shields customization, dashboard and diagnostics, regression and security tests. Other previous Z Browser requirements remain part of production scope.
